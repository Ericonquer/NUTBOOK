# Nutbook Skill 自动接入与标签模型设计

> 面向 Nutbook 下一阶段产品化的短设计。目标是先统一规则，再实现功能，避免继续在“猜 skill 输出目录”和“标签语义不清”上反复返工。

## 1. 设计结论

Nutbook 下一阶段围绕两条主线推进：

1. `Skill 自动接入`
2. `文件三类标签模型`

核心原则：

- Nutbook 不负责“猜 skill 到底把文件生成到哪里”
- Nutbook 优先读取 skill 的显式输出目录声明
- 标签不是无限制扩张，而是固定为三类信息：
  - 自定义标签
  - skill 来源标签
  - 文件类型标签

## 2. Skill 自动接入

### 2.1 问题定义

当前 skill 的输出目录不稳定：

- 有的放在 workspace 根目录
- 有的放在 skill 自己目录下的 `output/`
- 有的放在 `example/`
- 有的放在 `user/`

如果 Nutbook 去猜这些目录，会带来几个问题：

1. 规则会越来越多，维护成本高
2. skill 作者的自由命名会持续破坏自动发现稳定性
3. Nutbook 会被迫承担 skill 生态没有统一规范的复杂度

因此，这不是一个“扫描算法优化”问题，而是一个“约定先于扫描”问题。

### 2.2 目标规则

Nutbook 对 skill 输出目录采用三层优先级：

1. `显式声明优先`
2. `约定默认值兜底`
3. `未命中则不自动接入`

#### 第一优先：显式声明

如果 skill 的 `SKILL.md` / `skill.md` 中声明了输出目录，Nutbook 直接使用该目录。

第一阶段约束：

- 优先读取 `YAML frontmatter`
- 正式字段只认一个：

```md
artifact_output_dir: output
```

- 只接受相对 skill 根目录的路径
- 不接受绝对路径作为第一阶段自动接入输入

推荐写法：

```md
artifact_output_dir: output
```

Nutbook 第一阶段不再并行支持多个正式字段名，避免解析规则漂移。

#### 第二优先：默认值兜底

如果 skill 没有显式声明，但它属于“会产出文件的 skill”，Nutbook 默认尝试一组白名单目录名：

```text
<skill_root>/output
<skill_root>/outputs
<skill_root>/dist
<skill_root>/export
<skill_root>/exports
<skill_root>/result
<skill_root>/results
<skill_root>/artifacts
<skill_root>/deliverables
<skill_root>/reports
```

也就是：

- 目录名来自固定白名单
- 位置固定在 skill 根目录下
- 不扫描白名单之外的自由命名目录

#### 第三优先：不自动接入

如果：

- 没有显式声明
- 也没有标准 `output/`

则 Nutbook：

- 不自动接入
- 只在 skill 发现面板中提示“未发现标准输出目录”

### 2.3 自动接入目录安全规则

自动接入不仅要看“能不能找到目录”，还要看“这个目录是不是适合作为生成物资料库”。

Nutbook 必须拒绝以下目录作为自动接入目标：

- OpenClaw workspace 根目录
- Hermes workspace 根目录
- 任何明显过宽的父级工作目录

原因：

1. 这些目录通常包含系统协作文件
2. 会把非生成物文件一起扫进 Nutbook
3. 会污染文件列表与标签体系

典型误扫文件包括：

- `SOUL.md`
- `USER.md`
- `MEMORY.md`
- 协作文档
- 其他项目源码与说明文件

因此，自动接入只接受：

1. skill 显式声明的专用输出子目录
2. skill 根目录下命中白名单的专用输出子目录

如果 skill 声明的输出目录直接指向 workspace 根目录，Nutbook 的行为应该是：

- 不自动接入
- 在 skill 来源面板中标记为“输出目录过宽”
- 提示用户将 skill 改为独立 `output/` 子目录后再接入

### 2.4 Nutbook 的行为边界

Nutbook 只负责：

- 发现 skill
- 解析输出目录声明
- 建议或自动接入对应目录

Nutbook 不负责：

- 修改 skill 执行逻辑
- 猜测任意自定义目录结构
- 为没有规范的 skill 做复杂兼容推断

### 2.5 产品形态

设置中新增一个独立一级页签：`Skill 接入`。

它不再并入 `文件管理`，职责只包括：

- 扫描已安装 skill
- 显示 skill 接入状态
- 提供接入 / 手动接入 / 排除

它不负责：

- 文件扫描
- 文件来源管理
- 已移除文件恢复

也就是说：

- `Skill 接入` 负责候选发现与接入判断
- `文件管理` 负责真实 source 管理

### 2.6 去重与分组规则

OpenClaw 与 Hermes 之间可能存在大量重复 skill。

因此，Nutbook 不能按“扫描到几个目录就列几条”直接展示，而必须先做 `逻辑 skill` 去重。

第一阶段去重规则：

1. 优先使用 frontmatter `name`
2. 没有 `name` 时，退回 skill 根目录名
3. 名称归一化：
   - 全部转小写
   - 忽略空格差异
   - 忽略 `_` / `-` 差异

同一个逻辑 skill 的多个安装副本，应在 UI 中聚合为一条，并记录“发现了几个副本”。

第一阶段副本优先级：

1. `~/.openclaw/skills`
2. `~/.openclaw/workspace/skills`
3. `~/.agents/skills`
4. `~/.codex/skills`

也就是说：

- UI 主列表按逻辑 skill 聚合
- 技术实现上仍可保留原始副本信息

### 2.7 Skill 状态模型

`Skill 接入` 不再只显示“产物型 skill”，而是显示扫描到的逻辑 skill，并分成以下状态：

1. `已接入`
2. `可接入`
3. `待手动接入`
4. `已排除`

含义：

- `已接入`
  - 已经绑定到 Nutbook 的真实 source

- `可接入`
  - 已识别到合法输出目录，可直接接入

- `待手动接入`
  - 已扫描到 skill，但未识别出标准输出目录
  - 用户可手动指定该 skill 的产物目录并接入

- `已排除`
  - 用户明确标记为不纳入 Nutbook 管理

### 2.8 列表展示规则

`Skill 接入` 不直接铺成高卡片列表，而采用紧凑一行式信息展示。

每条 skill 显示：

- skill 名称
- 状态 badge
- 输出目录或状态说明
- 右侧主按钮

右侧主按钮根据状态变化：

- `已接入`
- `接入`
- `手动接入`
- `已排除`

同时提供一个次级操作：

- `排除`

推荐分组视图：

1. `已接入 / 可接入`
2. `待手动接入`
3. `已排除`

默认只展开前两组，`已排除` 可折叠。

这样可以解决：

1. Hermes / OpenClaw 重复 skill 导致列表膨胀
2. 非产物 skill 过多导致界面过长
3. 第一次扫描时无法快速清洗无关 skill

### 2.9 排除机制

对于明确不归 Nutbook 管理的 skill，例如：

- review
- weather
- 纯查询类
- 纯流程类

用户应能在 `Skill 接入` 中手动点击 `排除`。

排除后：

- 该 skill 不再出现在主分组中
- 被放入 `已排除` 分组
- 状态持久化到 Nutbook 本地配置

这不是删除 skill，也不是卸载 skill，只是告诉 Nutbook：

`以后不要把它当成产物管理对象`

### 2.10 推荐实现顺序

第一步：

- 扫描 OpenClaw / Hermes 约定的 skill 安装目录
- 找到 `SKILL.md` / `skill.md`
- 解析 `artifact_output_dir`
- 聚合成逻辑 skill

第二步：

- 如果无显式声明，则尝试 skill 根目录下的白名单目录名
- 如果仍未识别输出目录，则进入 `待手动接入`

第三步：

- 对 `可接入` skill，生成 Nutbook 中的 `folder source`
- 对 `待手动接入` skill，允许用户手动选择产物目录
- 对无关 skill，允许用户排除

### 2.11 Source 与 Skill 绑定约束

为控制复杂度，第一阶段采用以下硬约束：

1. `一个 source 只绑定一个主 skill`
2. `一个 skill 可以对应多个 source`，但每个 source 仍只认一个主 skill
3. skill 绑定的职责是：
   - 提供 skill 来源标签
   - 提供来源说明
   - 不改变 source 本身仍然是 `folder source` 的事实

这样可以避免：

- 多 skill 共绑一个 source 带来的来源歧义
- skill 标签继承规则迅速复杂化

## 3. 标签模型

### 3.1 目标

Nutbook 的标签不做成通用无限系统，而是固定为三类：

1. `自定义标签`
2. `skill 来源标签`
3. `文件类型标签`

这样做的目标是：

- 控制卡片信息密度
- 保持标签语义清楚
- 让 AI 生成物管理器的定位更明确

### 3.2 三类标签定义

#### 自定义标签

由用户手动维护。

示例：

- 演示稿
- 待整理
- 可复用

第一阶段建议：

- 每个文件最多显示 1 个主自定义标签
- 自定义标签采用单选模型
- 先不把多标签编辑做得过重

#### skill 来源标签

由系统自动生成，来源于文件所属 source 对应的 skill。

示例：

- html-ppt
- gemini
- notebooklm

规则：

- 默认只读
- 不建议用户手动改名
- 当文件所属 source 已绑定 skill 时自动继承

#### 文件类型标签

由系统自动生成。

示例：

- HTML
- Markdown

这类标签已经存在，应继续保留。

### 3.3 展示顺序

卡片与文件页统一按以下顺序显示：

```text
自定义标签 → skill 标签 → 类型标签
```

原因：

1. 自定义标签是用户最关心的主观分类
2. skill 标签表达来源，适合放中间
3. 类型标签放最右，便于在右下区域稳定识别

### 3.4 展示位置

#### 文件卡片

显示在当前类型标签那一排。

顺序：

```text
自定义标签 → skill 标签 → 类型标签
```

第一阶段约束：

- 文件卡片只负责显示标签
- 文件卡片不承担自定义标签编辑

#### 打开文件后

显示在文件路径栏右侧按钮的左边。

也就是：

```text
路径信息 | 自定义标签 | skill 标签 | 类型标签 | 收藏 | 移除 | 更多
```

### 3.5 文件页标签交互

打开文件后的标签管理不放进 `更多` 菜单，而是直接在路径栏标签区完成。

这里采用统一的 `宿主 overlay toolbar` 方案，而不是让 Markdown 和 HTML 各自使用不同技术实现。

原因：

- HTML 页面下普通 DOM toolbar 曾经被 child webview 层级压住
- 如果 Markdown 继续走普通 DOM、HTML 再走另一套 overlay，会重复出现：
  - 图标尺寸不一致
  - tooltip/menu 层级错乱
  - hover 叠加
  - 菜单被切割

因此，这一整条文件页顶部交互带统一约束为：

- `md/html` 共用同一套宿主 overlay toolbar
- 标签、收藏、移除、更多、tooltip、popover 都使用同一套宿主层交互系统
- 不允许 `md` 一套、`html` 一套分别实现

### 3.5.1 宿主 overlay 交互规则

为避免再次出现 tooltip/menu 叠加和层级问题，文件页顶部统一采用以下规则：

1. 同一时刻只允许一个 tooltip 可见
2. `更多` 菜单展开时，对应 tooltip 自动关闭
3. 标签编辑 popover 打开时，其他 tooltip 与 popover 全部关闭
4. 所有轻浮层共享一个统一的 overlay root
5. 所有浮层共用同一套关闭机制：
   - click outside 关闭
   - `Esc` 关闭
   - 切换标签页关闭
   - 关闭文件关闭

### 3.5.2 自定义标签编辑交互

自定义标签编辑采用轻量 popover，不使用大弹窗，也不跳转设置页。

规则：

1. `没有自定义标签时`
   - 在标签区最左侧显示一个 `+ 标签` 入口

2. `点击 + 标签`
   - 打开宿主层 popover
   - 内容包括：
     - 现有自定义标签列表
     - 新建标签输入框
     - 确认 / 取消

3. `已有自定义标签时`
   - 标签正常显示在路径栏
   - hover 后出现轻量操作：
     - 编辑
     - 删除

4. `编辑`
   - 仍在原位 popover 内完成
   - 不打开大弹窗
   - 不放进 `更多` 菜单

规则如下：

1. `自定义标签`
   - 直接显示在路径栏中
   - 是文件页的主标签编辑入口
   - hover 后出现轻量操作：
     - 编辑
     - 删除

2. `skill 标签`
   - 只读显示
   - 不提供 hover 编辑

3. `类型标签`
   - 只读显示
   - 不提供 hover 编辑

4. `新增自定义标签`
   - 通过路径栏标签区中的空白入口或新增按钮完成
   - 不放进 `更多` 菜单

这样做的原因：

- 标签属于文件身份信息，不属于次级操作
- `更多` 菜单只保留编辑、导出、演示模式之类的动作
- 只有自定义标签需要高频编辑，hover 交互足够，不需要长按

### 3.6 编辑入口

标签编辑不放在设置页完成，而放在文件操作上下文中。

#### 文件卡片

第一阶段不提供标签编辑，只显示标签状态。

#### 打开文件后

直接在路径栏标签区管理自定义标签，不通过 `更多` 菜单进入。

#### 设置页

设置页中的 `标签管理` 只负责：

- 新增标签
- 重命名标签
- 删除标签

不负责直接给文件打标签。

### 3.7 数据规则

建议第一阶段按以下规则落地：

- `文件类型标签`：系统自动写入，不可编辑
- `skill 标签`：系统自动关联，不可编辑
- `自定义标签`：用户可编辑

实现上仍然可以复用当前 `tags / item_tags` 结构，但需要给标签增加来源语义：

- `system:file-type`
- `system:skill`
- `custom`

这层可以先作为应用层字段，不一定第一步就改数据库结构。

## 4. 推荐推进顺序

### Phase A

先做 `skill 自动发现 + 手动接入`：

- 只发现
- 只列出
- 只让用户确认接入

### Phase B

做 `skill 来源标签自动继承`：

- source 绑定 skill
- source 下文件自动带上 skill 标签

### Phase C

做 `自定义标签打标入口`：

- 文件卡片入口
- 文件页入口

### Phase D

完善 `标签管理页`：

- 只管标签定义
- 不做文件级分配

## 5. 设计结论

Nutbook 后续不应该继续通过“猜 skill 输出目录”来自动接入，也不应该把标签系统做成泛化而失控的无限模型。

更稳的方向是：

- 用 `skill 输出目录约定` 解决自动接入
- 用 `三类标签模型` 解决文件语义表达

这两条一起成立后，Nutbook 才真正具备“AI 生成物管理器”的识别能力，而不是只是一个本地文件浏览器。
