# Nutbook 缩略图引擎路线决策表

> 面向 Nutbook 当前安装版收尾与后续版本演进的短决策文档。目标不是一次性决定终局架构，而是先明确 `1.0 / 1.1 / 1.2` 各自解决什么问题，避免在截图引擎这条线上反复返工。

## 1. 背景

Nutbook 当前已经支持：

- HTML / Markdown 文件的缩略图生成
- 默认 SVG 占位图回退
- 用户手动启用系统 Chrome 作为截图引擎
- 前端状态提示当前缩略图生成进度

当前主要矛盾不是“能不能截图”，而是：

1. 首次扫描大量文件时，截图链路容易带来卡顿感
2. 如果直接调用系统 Chrome，用户容易感到突兀或不安全
3. 不同机器上的浏览器环境不一致，影响安装版体验

因此，缩略图系统需要分阶段推进，而不是一口气上最重架构。

## 2. 路线候选

| 方案 | 用户体验 | 开发复杂度 | 安装包体积 | 跨机器稳定性 | 适合阶段 | 判断 |
| --- | --- | --- | --- | --- | --- | --- |
| `A. 用户授权的系统 Chrome 队列截图` | 中等 | 低到中 | 小 | 一般 | `1.0` | 先交付的现实方案 |
| `B. 安装包内置 headless-shell / Playwright Chromium` | 高 | 中 | 大 | 高 | `1.1` | 正式发行版优先方案 |
| `C. 常驻 Chrome Worker（DevTools / CDP）` | 很高 | 高 | 小到中 | 取决于环境 | `1.2` | 最强，但不应抢在前面做 |
| `D. 原生 QuickLook / WebKit 截图` | 低到中 | 中 | 小 | 低 | 不建议主线 | 对 JS HTML 不稳定 |
| `E. 独立 Node / Playwright helper` | 高 | 中到高 | 中到大 | 高 | 备选 | Rust 直连 CDP 太重时可转向 |

## 3. 各方案说明

### 3.1 `A. 用户授权的系统 Chrome 队列截图`

这是 Nutbook `1.0` 应采用的方案。

核心原则：

- 默认不静默调用系统 Chrome
- 没有截图引擎时，先正常显示文件与 SVG 占位图
- 只有用户在设置中明确启用后，才允许系统 Chrome 参与截图
- 状态栏必须明确显示：

```text
正在调用 Chrome 截取文件缩略图 x/y
```

优点：

- 开发改动最小
- 能快速交付安装版
- 用户对外部程序调用有知情权

缺点：

- 仍然依赖系统 Chrome
- 如果底层仍是一张图一次 CLI，体验仍不够平滑

### 3.2 `B. 安装包内置 headless-shell / Playwright Chromium`

这是 Nutbook `1.1` 最值得优先评估的方向。

核心目标：

- 不依赖用户机器是否安装 Chrome
- 缩略图体验在不同 Mac 上保持一致
- 避免系统菜单栏 / Dock 上出现 Chrome 跳动

优点：

- 安装即用
- 用户体验明显更专业
- 适合正式对外分发

缺点：

- 安装包体积显著增大
- Apple 签名、公证、路径处理复杂度上升

这一步解决的是“发行质量”和“环境一致性”，对安装版价值很高。

### 3.3 `C. 常驻 Chrome Worker（DevTools / CDP）`

这是 Nutbook `1.2` 可以重点推进的架构升级。

它不是简单的“换个参数调用 Chrome”，而是一个后台截图子系统：

- 启动一次 Chrome
- 保持一个长期截图会话
- 通过 DevTools Protocol 控制页面导航与截图
- 维护任务队列、去重、取消与异常恢复

优点：

- 系统 Chrome 也可以做到只启动一次
- 大批量文件扫描的效率和稳定性最好
- 为未来更复杂的预渲染能力打基础

缺点：

- 后端架构复杂度高
- 需要额外依赖或协议实现
- 不适合在 `1.0` 收尾阶段夹带推进

结论：

这条路线值得做，但应该作为单独工程，而不是与当前安装版细节修补混在一起。

## 4. Nutbook 的阶段建议

### 4.1 `Nutbook 1.0`

目标：先把安装版做成“可交付软件”。

采用：

- `A. 用户授权的系统 Chrome 队列截图`

完成标准：

- 默认 SVG 占位，不阻塞文件显示
- 用户可以在设置中明确启用系统 Chrome
- 状态栏清楚提示是否在调用 Chrome
- 无截图引擎时，有明确说明与安装引导

这一阶段不追求“最优截图架构”，只追求：

- 安全感
- 可解释性
- 不假死
- 可安装

### 4.2 `Nutbook 1.1`

目标：提升正式发行质量。

优先推进：

- `B. 安装包内置 headless-shell / Playwright Chromium`

完成标准：

- 新机器安装后无需再额外安装截图引擎
- HTML / Markdown 缩略图行为一致
- 不再依赖系统 Chrome 是否存在

这一阶段优先级高于 `C`，因为它直接影响跨机器安装体验。

### 4.3 `Nutbook 1.2`

目标：提升缩略图引擎的架构质量和扫描效率。

优先推进：

- `C. 常驻 Chrome Worker`

完成标准：

- 截图引擎具备长期会话能力
- 批量扫描时不再一张图启动一次浏览器
- 任务队列、取消、失败恢复都有明确状态

## 5. 当前结论

Nutbook 目前应继续按照 `1.0` 路线推进：

1. 先把“默认占位 + 用户授权系统 Chrome + 状态提示 + 设置引导”做稳
2. 不在当前阶段直接引入 `常驻 Chrome Worker`
3. 后续是否继续升级到 `1.1 / 1.2`，再根据安装版测试反馈单独决策

一句话总结：

> `1.0` 先解决“能安心用”，`1.1` 再解决“装上就能用”，`1.2` 最后解决“批量用起来也丝滑”。
